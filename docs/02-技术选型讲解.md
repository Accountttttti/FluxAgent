# 技术选型讲解（含名词解释）

> 本文是「聊天界面前端性能优化」技术选型的教学笔记。面向：用过 Vue 3、没接触过 React 的读者。

## 先建立一个大背景

这三个优化都针对「聊天界面」这个场景。核心概念：

- **流式（streaming）**：AI 不是一次性把整段回答想好再发，而是**边生成边吐字**，像打字机一样。你看到字一个个冒出来，就是流式。
- **token**：LLM 处理文字的最小单位，约等于「半个到一两个汉字 / 英文单词」。流式速度大约每秒 20–100 个 token。

---

## ① zustand + requestAnimationFrame —— 解决「字冒太快，界面卡」

### 问题是什么
token 每秒几十个，如果每来一个 token 就让 React 重画一次界面，一秒要画几十上百次，就会卡。

### 方案
把「数据到达」和「React 渲染」**解耦**：
1. 用 zustand 的 `subscribe`（在 React 组件外）监听 token，累积到一个 buffer（缓冲区）；
2. 用 `requestAnimationFrame`（或 30–60ms 的 throttle 节流）把一帧内到达的多个 token **合并成一次提交**给 React。
3. 用 `React.memo` 保证只有「正在流式输出那条消息」在重画，历史消息不动。

### 名词解释
| 名词 | 大白话 | 类比 Vue |
|---|---|---|
| zustand | 状态管理库，集中管全局数据（消息列表等） | Pinia 的角色 |
| re-render | 数据变了，组件重画一遍界面 | 响应式更新（但 React 是手动的） |
| requestAnimationFrame (rAF) | 浏览器定时器，跟屏幕刷新对齐，一秒约 60 次 | — |
| throttle（节流） | 把高频触发合并成低频执行 | — |
| buffer（缓冲区） | 临时攒数据的地方 | — |
| React.memo | 给组件加记忆，数据没变就不重画 | computed 的缓存感 |

## ② markdown 解析 —— 解决「AI 回复有格式，流式到一半会乱」

### 问题是什么
AI 回复经常是 markdown 格式。但流式过程中 markdown 是**残缺的**（代码块 ` ``` ` 只开了头、结尾还没生成），直接渲染会闪烁/错乱。此外渲染的是模型输出，有安全风险。

### 方案
- 库组合：`react-markdown` + `remark-gfm`（表格）+ `rehype-highlight`（代码高亮）+ `rehype-sanitize`（清洗）。
- 流式期间先用「轻量/纯文本」渲染，**代码块闭合后再做完整 markdown 渲染**；或用专门的流式 markdown 库（`react-streaming-markdown` / `streamdown`）。
- 大段内容用 `useMemo` 按 message id 缓存，避免每次 token 重新解析全文。

### 名词解释
| 名词 | 大白话 |
|---|---|
| markdown | 轻量标记语言，`# 标题`、`**加粗**`、` ```代码``` ` 渲染后变排版好的文字 |
| react-markdown | 把 markdown 渲染成 React 界面的库 |
| remark-gfm | 插件，支持表格、任务列表（GFM = GitHub Flavored Markdown） |
| rehype-highlight | 插件，给代码块加语法高亮 |
| rehype-sanitize | 插件，清洗 HTML，防 XSS |
| XSS（跨站脚本攻击） | 恶意脚本被执行的安全攻击。渲染 AI 输出必须消毒 |
| useMemo | React 里「缓存计算结果」，避免重复计算 |

## ③ IndexedDB —— 解决「历史太多，存不下/存了卡」

### 问题是什么
聊天历史可能有几万条，`localStorage` 只有 ~5MB 且同步（会卡），存不下大历史。

### 方案
用 `IndexedDB`（浏览器本地数据库，容量大、异步不卡界面），配合 `Dexie.js` 或 `idb` 封装。按 session 存 message，索引 `sessionId + timestamp`，大历史用**分页/虚拟滚动懒加载**。

### 名词解释
| 名词 | 大白话 |
|---|---|
| IndexedDB | 浏览器自带本地数据库，容量大（几百 MB~GB 级），异步 |
| localStorage | 浏览器小仓库，~5MB，同步（会卡） |
| Dexie.js / idb | 给 IndexedDB 包的「好用外壳」，原生 API 太啰嗦 |
| session（会话） | 一次连续对话 = 一个会话 |
| 索引（index） | 数据库里加速查找的东西 |
| 虚拟滚动（virtual scroll） | 只画屏幕看得见的几条，滚到哪画到哪 |

## 一句话总结

「高频流式渲染」和「大历史持久化」是聊天 agent 前端最真实的两个难点，本文的选型（zustand + rAF、react-markdown、IndexedDB/Dexie）是当前主流方案。

## 常见疑问 FAQ

### Q1：为什么要流式？让 AI 一次性输出不行吗？
流式是「体验驱动」的选择，不是技术必须。一次性输出用户要干等十几秒到几十秒；流式让用户立刻看到回应，降低等待焦虑。主流产品都做流式。

### Q2：字冒太快页面一定卡吗？
不一定。卡是「没优化」导致的（每 token 都重画全列表 + 重解析 markdown）。做了 rAF 合并 + 只渲染活动消息 + useMemo 缓存就不会卡。

### Q3：原版 nanobot 没解决吗？有必要优化吗？
nanobot 其实**明确做了这些优化**——它的前端是 React 18 + TS + Vite，流式渲染用「animation-frame 合并、节流 markdown、窗口化历史、代码高亮懒加载」（见 PR #3877），和我们选的方案几乎一致。所以我们不是「修 nanobot 的 bug」，而是**重做 + 理解原理 + 能讲清楚**——这本身就是面试能讲出深度的点，也反过来说明这些优化是真必要（连 41k star 的项目都得专门做）。

### Q4：四个库组合解决什么？
把 AI 返回的 markdown 文本（纯字符串）渲染成「安全、漂亮、带表格和代码高亮」的网页：react-markdown 解析渲染、remark-gfm 支持表格、rehype-highlight 代码高亮、rehype-sanitize 防 XSS。

### Q5：IndexedDB+Dexie 是什么？跟「1g 压到 0.1g」是一回事吗？
不是一回事，是两个层面：
- IndexedDB+Dexie = **存储层**（把完整历史存在浏览器本地、怎么查得快）。
- 「1g→0.1g 压缩」= **记忆管理层**（LLM 上下文窗口有限，需要压缩/摘要旧历史腾空间，属于阶段 2 的「记忆」）。
- 两者配合：IndexedDB 存完整历史，记忆管理从中取「最近 N 条 + 摘要」塞进上下文窗口。
