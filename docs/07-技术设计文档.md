# FluxAgent 技术设计文档

> 项目：FluxAgent（复刻 HKUDS/nanobot 核心能力的个人 AI agent 应用）。
> 本文档是阶段 1 的实现依据，按「正经公司技术方案」的结构组织。

## 1. 背景与目标

**背景**：做一个个人 AI agent 应用，复刻 nanobot 的核心能力，作为学习 + 实习作品集。

**目标**：
1. 复刻 nanobot 核心骨架（后端 agent + 前端聊天 UI，含流式渲染、markdown 解析、IndexedDB 持久化等前端优化——nanobot 已有成熟方案，直接复刻即可）。
2. UI 做得更好看。
3. 边做边学，产出教学笔记 + 面试准备。

**非目标（本期不做）**：MCP 全量支持、多 agent 工作流、Telegram/Discord 等聊天渠道、远程 SSH/多实例、自动化定时任务。这些留到阶段 2/3 或砍掉。

## 2. 需求分析

**功能需求**：
- 单会话聊天（阶段 1），多会话（阶段 2）
- 流式回复（边生成边显示）
- 历史本地持久化（刷新页面还在）
- markdown 渲染 + 代码高亮
- 消息发送/接收状态（发送中 / 已接收 / 失败）

**非功能需求**：
- 流式渲染不卡顿（合并节流）
- 大历史不卡（窗口化 / 虚拟滚动）
- 数据安全（markdown 消毒，防 XSS）

## 3. 现状分析

nanobot 现状见 [`docs/06-nanobot架构拆解.md`](./06-nanobot架构拆解.md)。核心结论：后端是大脑（agent/会话/工具/记忆），前端是瘦客户端，靠 WebSocket 通信。我们复刻「核心骨架」而非 1:1。

## 4. 总体方案设计

**架构图（文字版）**：

```
┌─────────────┐   HTTP POST + SSE 流式   ┌──────────────┐   OpenAI 兼容 API   ┌──────────┐
│  React 前端  │ ───────────────────────▶ │ FastAPI 后端  │ ──────────────────▶ │ DeepSeek │
│  (浏览器)    │ ◀─────────────────────── │  (Python)     │ ◀────────────────── │          │
└─────────────┘                          └──────────────┘                      └──────────┘
       │
       └── IndexedDB（本地历史持久化）
```

**技术选型与理由**：

| 层 | 选型 | 理由 |
|---|---|---|
| 前端框架 | React 18 + TypeScript + Vite | 生态成熟、面试标准；TS 提升可维护性 |
| 状态管理 | **zustand** | 比 Context/reducer（nanobot 用）更简单直观，适合学习；selector 订阅避免多余 re-render |
| 流式渲染 | zustand subscribe + rAF/节流合并 | 把 token 到达与 React 渲染解耦，一帧合并一次 |
| markdown | react-markdown + remark-gfm + rehype-highlight + rehype-sanitize | 标准方案；sanitize 防 XSS（nanobot 用 streamdown，是替代项） |
| 持久化 | Dexie.js（IndexedDB 封装） | 容量大、异步；Dexie 屏蔽原生啰嗦 API |
| 后端框架 | FastAPI + openai SDK | FastAPI 轻量、支持异步/SSE；openai SDK 兼容 DeepSeek |
| 通信 | **SSE**（阶段 1） | 比 WebSocket 简单、够用；客户端 POST 发消息、服务端 SSE 流式返回 |

**关键决策：为什么阶段 1 用 SSE 而不是 nanobot 的 WebSocket？**
- 阶段 1 是最小闭环，只需「客户端发一条消息 → 服务端流式返回」，SSE（单向流）完全够用且简单得多。
- WebSocket 是双向长连接，适合「服务端主动推送、工具调用进度、中止生成」等复杂场景——这些阶段 2 再引入。
- 教学上：先学会 SSE（理解流式本质），再学 WebSocket 是合理的渐进路线。

## 5. 核心模块设计

**后端（backend/）**：
- `main.py`：FastAPI 应用 + 路由注册
- `chat.py`：聊天端点 `POST /api/chat`（接收消息列表，返回 SSE 流）
- `llm.py`：DeepSeek 客户端封装（openai SDK，`stream=True`）

**前端（frontend/）**：
- `store/`：zustand store（消息列表、会话、流式状态）
- `hooks/useStreaming.ts`：流式处理 + rAF 合并
- `components/`：`ChatView`、`MessageList`、`MessageBubble`、`MarkdownText`、`CodeBlock`、`Composer`
- `lib/api.ts`：fetch + SSE 读取
- `lib/db.ts`：Dexie 封装（IndexedDB）

## 6. 数据模型

**前端 IndexedDB（Dexie）schema**：

```ts
// 会话表
sessions: { id, title, createdAt, updatedAt }
// 消息表
messages: { id, sessionId, role, content, createdAt }  // role: user | assistant
```

索引：`messages` 按 `sessionId + createdAt` 加速查询。

## 7. 接口设计

| 方法 | 路径 | 说明 |
|---|---|---|
| POST | `/api/chat` | body `{ messages: [{role, content}] }`，响应 SSE（`data: {"delta":"..."}`） |
| GET | `/api/health` | 健康检查 |

## 8. 关键流程

**发一条消息的完整流程**：

1. 用户在 `Composer` 输入 → 前端往 zustand 追加 user 消息（乐观更新）
2. 前端 `POST /api/chat` 带上完整消息历史
3. 后端 `llm.py` 调 DeepSeek（`stream=True`）
4. DeepSeek 边生成边返回 token → 后端转成 SSE `data:` 块 → 回传前端
5. 前端用 `fetch` 读取流 → 把 delta 累积进 zustand 的 buffer
6. `useStreaming` 用 **rAF/节流合并**，每帧把 buffer flush 成一次渲染（不是每 token 渲染）
7. 流结束 → 把完整消息写入 IndexedDB

## 9. 技术难点与风险

| 难点 | 方案 |
|---|---|
| 流式 markdown 残缺（代码块未闭合） | 流式期间轻量渲染，闭合后再完整渲染 |
| XSS（渲染模型输出） | rehype-sanitize 消毒 |
| 流式渲染卡顿 | zustand subscribe + rAF 合并 |
| 大历史卡顿 | Dexie 分页 + 虚拟滚动 |
| 风险：DeepSeek key 未申请 | 先注册拿 key，存环境变量 `DEEPSEEK_API_KEY` |

## 10. 测试方案

- 后端：pytest，`chat.py` 用 mock 的 LLM 流测 SSE 输出
- 前端：Vitest，测 store/reducer（消息投影、流式合并逻辑）

## 11. 部署运维

- 本地开发：`uvicorn main:app --reload` 起后端 + `npm run dev` 起前端
- 环境变量：`DEEPSEEK_API_KEY`
- 阶段 1 不做容器化/CI，本地跑通即可
