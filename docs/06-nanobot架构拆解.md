# nanobot 架构拆解（讲解版）

> 阶段 0 产出。来源：`reference/nanobot`（HKUDS/nanobot，MIT 协议）。
> 读法：每个模块先给「技术描述」，紧接着「大白话」和「名词解释」，方便对照着看。

## 0. 一句话定位

nanobot 是一个**个人 AI agent 框架**。它自己 `AGENTS.md` 里写了一句核心设计原则：

> Python 网关负责 agent 执行、会话、工具、记忆、安全策略；WebUI 和 TUI 只是「瘦客户端」，共享同一个运行时，执行和策略逻辑一律不放客户端。

**大白话**：这个项目把「聪明的大脑」放在后端（Python），前端只是「遥控器 / 显示器」。所有真正做决策、调模型、记东西的逻辑都在后端，前端只负责「把字显示出来、把你说的话发过去」。

**名词解释**：
- **agent（智能体）**：一个能「自己调用工具、记住上下文、一步步完成任务」的 AI 程序，而不只是「一问一答」的聊天机器人。
- **网关（gateway）**：后端那个「常驻运行、统一对外服务」的进程，网页前端和终端都连它。
- **瘦客户端**：不含业务逻辑、只做展示和交互的前端。

## 1. 整体结构（monorepo）

```
nanobot/
├── nanobot/            # Python 后端（大脑）
├── webui/              # React 前端（网页版遥控器）
├── tui/                # 终端前端（命令行版遥控器）
├── packages/client-events/  # 前后端共享的事件类型定义
├── docs/  tests/  scripts/
└── pyproject.toml      # Python 依赖 + 入口
```

**大白话**：一个仓库里同时装着「后端、网页前端、终端前端」三块。

**名词解释**：
- **monorepo**：把多个相关项目放在同一个 git 仓库里管理（相对的是「每个项目一个仓库」）。
- **预构建**：前端写完是 TypeScript 源码，浏览器不认识，得先用 Vite「打包」成静态 HTML/JS。nanobot 把打包好的静态文件塞进 Python 包，所以用户装一个 Python 包就自带网页界面。

## 2. 后端模块（nanobot/）

### agent/ —— 大脑核心
**技术**：对话循环、上下文/记忆、工具、子 agent。核心文件 `loop.py`、`runner.py`、`memory.py`。

**大白话**：整个项目最重要的一坨。负责「收到你一句话之后，怎么一步步思考、调用工具、把回答生成出来」的完整循环。

**名词解释**：
- **对话循环（agent loop）**：agent 反复「思考 → 行动 → 观察结果 → 再思考」直到任务完成的循环。
- **上下文（context）**：发给模型的所有内容（你的话 + 历史 + 系统设定），模型只能「看到」这些。
- **记忆（memory）**：让 agent 跨对话记住东西的机制（阶段 2 会讲）。

### providers/ —— LLM 适配层
**技术**：OpenAI 兼容、Anthropic、Bedrock 等模型接入，带重试/回退/流式。

**大白话**：不同公司的大模型接口长得不一样，这个模块把它们「翻译」成统一的一套，这样上层代码不关心你用的是 DeepSeek 还是 OpenAI。

**名词解释**：
- **适配层**：屏蔽不同实现差异、对外提供统一接口的一层。
- **LLM**：大语言模型（Large Language Model），就是 ChatGPT / DeepSeek 背后那类模型。

### session/ —— 会话管理
**技术**：会话状态与持久化（JSONL/SQLite）、历史、标题/摘要。

**大白话**：管「一次连续对话」这个东西——把它存下来、读出来、起标题、做摘要。

**名词解释**：
- **会话（session）**：一次连续的多轮对话。
- **持久化**：把数据从「内存（关了就没了）」写到「磁盘（存文件里，下次还能读）」。JSONL 是「每行一条 JSON」的文件格式，SQLite 是「单文件的轻量数据库」。

### bus/ —— 消息总线
**技术**：进程内异步消息队列，传递入站/出站消息。

**大白话**：一个「传送带」。各模块不直接互相调用，而是把消息丢到传送带上，对方从传送带取。这样模块之间解耦。

**名词解释**：
- **消息队列**：先进先出、异步传递消息的管道。
- **异步**：不用干等，事情在后台进行，完成再通知你。

### channels/ —— 聊天渠道
**技术**：Telegram/Slack/Discord 等渠道；其中 `websocket/` 是 WebUI/TUI 的传输。

**大白话**：让 agent 能「接进」不同的聊天软件。网页和终端也算一种「渠道」，通过 WebSocket 连进来。

**名词解释**：
- **WebSocket**：浏览器和服务器之间的一条「双向长连接」，建立后双方可随时互发消息（我们阶段 1 先用更简单的 SSE）。

### webui/ —— 网页后端
**技术**：HTTP 路由、WS 握手、token、出站投影（settings_*/remote_* 等一大堆文件）。

**大白话**：专门服务网页前端的后端代码——处理网页请求、管登录 token、把内部消息格式「投影」成前端要的样子。

**名词解释**：
- **握手（handshake）**：建立 WebSocket 连接前的「打招呼确认」过程。
- **投影（projection）**：把后端内部数据格式，转换成前端渲染需要的样子。

### api/ —— OpenAI 兼容接口
**技术**：独立 HTTP 服务器（/v1/chat/completions 等）。

**大白话**：让 nanobot 对外「假装自己是 OpenAI」，这样任何用 OpenAI SDK 写的程序都能直接连它。

**名词解释**：
- **OpenAI 兼容**：接口 URL、参数、返回格式都和 OpenAI 一样，换个 base_url 就能切换。

### gateway/ —— 网关进程管理
**技术**：后台网关进程的启动/停止/健康检查。

**大白话**：管「后端服务这个进程」的开关和状态。

**名词解释**：
- **进程（process）**：正在运行的一个程序实例。

### 其他模块（一句话）
- **command/**：斜杠命令（/xxx）的路由。
- **cron/**：定时任务（比如每天早上自动跑一次）。
- **skills/**：内置技能包（Markdown + shell 脚本）。
- **triggers/**：触发器（满足条件自动触发动作）。
- **security/**：网络/工作区访问策略（管 agent 能访问哪些网站/文件）。
- **config/**：配置（Pydantic schema）。
- **llm_usage/**：LLM 用量统计。

**名词解释**：
- **路由**：根据「你敲了什么命令 / 请求了什么路径」，决定交给哪个函数处理。
- **Pydantic**：Python 里做「数据校验」的库，配置用它保证格式正确。

## 3. 前端（webui/）

**技术栈**：React 18 + TypeScript + Vite + Tailwind + shadcn/ui（Radix）。

**大白话**：用 React 写的网页。Tailwind 管样式，shadcn/ui 是一套现成的漂亮组件库（按钮、输入框等）。

**状态管理**：不用 zustand/redux。用一个 `NanobotClient` 类（持有 socket、发送队列）+ React Context 暴露；消息投影用纯函数 reducer。

**大白话**：它管数据的方式是「一个专门的类 + React 的 Context 传递」，而不用我们选中的 zustand（我们的方案更简单直观）。

**名词解释**：
- **状态管理**：前端「全局数据放在哪、怎么改、怎么通知界面刷新」的一套机制。
- **Context**：React 自带的「跨组件传递数据」机制（类似 Vue 的 provide/inject）。
- **reducer**：一种「纯函数」——输入旧状态 + 一个事件，输出新状态，不改原数据。

**关键组件**（每个都是「界面的一块积木」）：
- `ThreadShell` — 对话主容器（把下面几个组件拼起来）
- `useNanobotStream` — 流式状态管理（核心，管「字怎么冒出来」）
- `ThreadViewport` — 窗口化历史（只显示最近一段）
- `ThreadComposer` — 输入框
- `MessageBubble` / `MarkdownText` / `CodeBlock` — 一条消息 / markdown 渲染 / 代码块
- `Sidebar` / `ChatList` — 侧边栏 / 会话列表

## 4. 通信方式

- **WebSocket**：实时聊天、事件推送
- **REST**：会话列表、设置等非流式操作
- **引导流程**：先 `GET /webui/bootstrap` 拿 token + ws 地址，再连 WebSocket
- **OpenAI 兼容 API**：`nanobot serve` 暴露 /v1/chat/completions

**名词解释**：
- **REST**：最常用的「HTTP 请求-响应」风格接口（GET 读、POST 写）。
- **SSE**：Server-Sent Events，服务器往浏览器「单向推送流」的技术（我们阶段 1 用这个）。
- **token（登录凭证）**：一串临时凭证，证明「你是谁、有没有权限连」。

## 5. 一条消息的完整旅程

发消息时数据怎么流：

1. 你在 `ThreadComposer` 输入 → 前端把消息发给后端
2. 后端 `WebSocketChannel` 收到 → 丢进消息总线（bus）
3. `AgentLoop` 消费消息 → 调 LLM
4. LLM 边生成边回调 → 转成 `delta` 事件 → 通过 WS 回传前端
5. 前端收到 delta → **合并节流** → reducer 投影成消息列表 → 渲染

**大白话**：你打字 → 前端发过去 → 后端 agent 开始「想」→ 模型一个字一个字吐出来 → 顺着原路流回你的屏幕。

## 6. 流式渲染优化（我们复刻的重点）

nanobot 做了这些（和我们选的方案一致）：

- **合并节流**：delta 事件攒起来，用 rAF 调度，每 **50ms（可见）/ 1s（隐藏标签页）** flush 一次，而不是每 token 渲染一次
- **窗口化历史**：只渲染最近 **120 条**，向上滚再加载 120 条
- **流式 markdown**：用 `streamdown` 处理「残缺 markdown」；代码高亮懒加载（流式时用纯 `<pre>`）

**名词解释**：
- **节流**：把高频触发合并成低频执行。
- **窗口化**：只渲染可见 / 最近的一部分，不渲染全部。
- **懒加载**：用到才加载，不用不加载。

## 7. 对我们的启示（复刻策略）

**重要发现**：nanobot 已经不是「4000 行」的小项目了——现在 `loop.py` 有 12 万字节、`ws_http.py` 9.6 万字节、`transcript.py` 9.3 万字节，还有大量 remote/ssh/settings 文件。它是一个**成熟的、大型的代码库**。

所以「1:1 全部复刻」既不现实、也没必要。我们要复刻的是**核心骨架**：

- 后端：agent loop（简化版）+ provider 适配 + session + WebSocket 通道
- 前端：流式渲染（合并节流 + 窗口化 + markdown）+ IndexedDB 持久化

这恰好印证了我们阶段 1 的「最小全栈闭环」思路是对的——先跑通骨架，再逐步加深。
